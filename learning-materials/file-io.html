1. 个人理解（先说人话）

前面几节里，你的数据都是自己手打进去的：ages = [18, 20, 17]、name = "张三"。 但真实的新闻数据不可能手打——你手上是宣传部发来的 Excel、是爬虫存下来的 .csv、 是录音转写软件导出的 .txt。所以「文件读写」这件事的本质是： 把程序外面的东西搬进内存，把内存里的结果搬出去存好。

只有两个动作：读（文件 → 内存）和写（内存 → 文件）。 但这两个动作里有三个非常具体的坑，几乎每个人第一次都会踩：

  1. 忘了关文件——程序跑一万次没事，跑第一万零一次崩了。用 with 一劳永逸。
  2. 编码不对——打开文件报 UnicodeDecodeError，或者满屏「锟斤拷」。这是中文用户特有的一关。
  3. CSV 的 newline=''——不写这一句，Windows 上导出的表格每行之间会多出一个空行。

还有一个经常被误会的现象：用 Excel 打开 UTF-8 的 CSV 变成乱码，这不是你代码的错。 后面第 6 节会专门讲这件事该怎么跟同事解释、怎么绕开。

「读文件」在 Python 里只有一种写法值得记：with open(路径, "r", encoding="utf-8") as f:。 把这句话当成一个整体背下来，就像背「新华社电」一样，不要拆开改。

2. 学习目标

学完这一份，你应该能做到：

  • 能用 open() 打开文件，并说清 "r" / "w" / "a" 三种模式的差别，特别是 "w" 会清空原文件这一点。
  • 能默写 with open(...) as f: 结构，并解释为什么它一定比 f = open(...) 好。
  • 遇到 UnicodeDecodeError 时知道这是编码问题，能按「先试 utf-8、再试 gbk、最后加 errors=」的顺序排查，而不是乱改代码。
  • 知道 utf-8-sig 是干什么的，能解释「BOM」是什么、为什么它会让你的数据表第一列列名变成 \ufeff标题。
  • 能用 csv.reader / csv.DictReader 读表格，用 csv.writer / csv.DictWriter 写表格，并记得 newline=''。
  • 能解释「Excel 打开 CSV 乱码」的成因，并给出两种可行的解决路径。
  • 知道文本 I/O 性能不如二进制 I/O，理解为什么读大文件时应该逐行迭代而不是一次性 read()。

4. 结构化解释

4.1 定义

先看官方文档对「打开文件」给出的最简形式：

open(filename, mode, encoding=None)
第一个参数是包含文件名的字符串；第二个参数是描述文件用途的字符串；第三个参数用来指定文件的编码。 ——引自 Python 官方教程《输入与输出》7.2.1 节「读写文件的方法」

官方在这一节给出的标准写法是： 

f = open('workfile', 'w', encoding="utf-8")

而关于 encoding 参数，官方有一句非常直接的建议：

处理文件对象时，最好使用 with 关键字。这样做的好处是，文件使用完毕后会自动关闭， 即使出现异常也是如此。……在文本模式下读取文件时，默认把平台特定的行结束符（Unix 上为 \n，Windows 上为 \r\n）转换为 \n。
因为 UTF-8 是现代事实上的标准，除非你知道你需要使用一个不同的编码，否则建议使用 encoding="utf-8"。 ——引自 Python 官方教程《输入与输出》7.2.1 节

4.2 最小模型：一个「文件柜」模型

把文件想象成办公室里的一个文件柜。你的程序不能直接把柜子里的纸抽出来用，必须：

  1. 打开柜门（open()）——你得先获得一个「把手」，也就是文件对象 f。
  2. 取 / 放纸（f.read() / f.write()）——所有操作都通过这个把手进行。
  3. 关柜门（f.close()）——不关，别人（甚至你自己）就打不开了，而且有些纸可能还没真正归档。

with 的作用是：你走出办公室的时候，门自动关上。 哪怕你中途摔了一跤（程序抛异常），门也会关。这就是官方说的「即使出现异常也是如此」。

现实类比Python 里对应什么忘了会怎样
文件柜磁盘上的一个文件文件不存在 → FileNotFoundError
把手（柜门把手）文件对象 f没把手就干不了任何事
柜门上贴的标签「只读 / 可写 / 追加」mode 参数标错标签：写进了只读文件 → PermissionError
柜子里的纸上的字用什么语言写的encoding 参数用错编码 → 打开全是天书（乱码）
出门顺手关门with 语句不关 → 资源泄漏，写的内容可能没落盘

这个模型能解释绝大多数新手困惑。比如「为什么 f.read() 之后 f.read() 又返回空字符串了？」 ——因为把手上的「读到哪儿了」这个位置一直在往前移，读到底了自然就什么都读不到了。 这不是 bug，是文件指针（官方术语叫「当前位置」）的正常行为。

4.3 关键机制一：mode 与 with

官方对模式字符的说明（《输入与输出》7.2.1 节）：

mode含义危险程度
"r"只读（默认）。文件必须已存在，否则 FileNotFoundError安全
"w"只写。会先清空原文件内容再写⚠ 会删数据
"a"追加。写在文件末尾，不删原内容较安全
"r+"读写，文件必须已存在注意文件指针
"b"二进制模式（可加在其它模式后，如 "rb"、"wb"）数据是 bytes
"t"文本模式（默认）正常
官方在讨论 open() 的 mode 时特别指出：'w' 模式打开的文件如果已经存在， 原有内容会被覆盖（清空）。所以写文件前请务必确认路径没写错—— open("data.csv", "w") 跑一次，你原来的 data.csv 就没了。

with 的返回值就是文件对象，所以 as f 里的 f 就是它。 官方还提到，文件关闭之后如果还去操作它，会抛 ValueError: I/O operation on closed file.； 可以用 f.closed 看文件是不是已经关了。

还有一个容易被忽略的官方提醒：

调用 f.write() 时，如果不使用 with 关键字，或者不调用 f.close()， 那么即使程序正常退出，也不能保证数据已经写入了磁盘。 ——引自 Python 官方教程《输入与输出》7.2.1 节

4.4 关键机制二：编码——中文用户的必修课

先分清两个东西：

  • 字符（character）：你看到的「新」「闻」这些字形。
  • 字节（byte）：磁盘上实际存的 0/1，以字节为单位。

编码（encoding）就是「字符 → 字节」的翻译规则，解码（decoding）是反向翻译。 用错规则去翻译，出来的就是乱码。

官方在 io 模块文档里把这件事说得非常重：

文本 I/O 的默认编码依赖于平台（即 locale.getencoding() 的返回值）…… 为此，强烈建议你在打开文本文件时显式地指定编码格式。 ——引自 Python 标准库 io 模块文档「文本 I/O」节

这句话背后的现实是：Windows 简体中文系统的默认编码是 GBK 系，而 macOS / Linux 默认是 UTF-8。 同一份代码，你在自己电脑上跑得好好的，交给同事就炸了——原因就在这儿。

编码家族速查：

编码名别称 / 备注典型场景
utf-8现代事实标准推荐默认选择；网页、GitHub、几乎所有现代工具
utf-8-sig带 BOM 的 UTF-8Windows 记事本、「另存为 CSV」、Excel 导出的 UTF-8 文件
gbk官方文档中作为 gb2312 类的代表列出老旧 Windows 软件导出的中文文本
gb18030GBK 的超集，覆盖更全当 gbk 也报错时可以试
big5繁体中文港澳台来源的文本

4.5 关键机制三：utf-8-sig 与 BOM

这个知识点门槛很低但坑人无数。官方文档 codecs 模块里有一段专门讲它：

Microsoft 发明了一种 UTF-8 的变体形式（Python 称之为 "utf-8-sig"）， 用于在文件中携带额外的签名信息。

在进行编码时，它会先写入一个 UTF-8 编码的 BOM（它看起来是这样一个字节序列：0xef, 0xbb, 0xbf）， 然后再写入编码后数据。在进行解码时，utf-8-sig 将跳过这三个字节。

在 UTF-8 中并不推荐使用 BOM，通常应当避免它们的出现。 ——引自 Python 标准库 codecs 模块文档「encodings.utf_8_sig」节

翻译成实际操作里的现象：

  • 你用 Excel 把表格「另存为 CSV UTF-8」，Excel 很可能给你加上了 BOM。
  • 然后你用 encoding="utf-8" 去读，程序不会报错——但它会把那三个字节也当成一个字符读进来。
  • 结果：你的第一列列名变成了 '\ufeff标题'。你在代码里写 row["标题"]，报 KeyError: '标题'。
  • 你盯着屏幕看半天，明明打印出来就是「标题」两个字啊——因为 \ufeff 是个零宽字符，看不见。
解决办法：读「可能是 Excel 存出来的 UTF-8 文件」时，用 encoding="utf-8-sig"。 它同时兼容「有 BOM」和「没有 BOM」两种情况，是处理这类文件最稳的选择。 验证方式：print(repr(列名))，就会看到 '\ufeff标题'。

4.6 关键机制四：errors 参数——解不开的时候怎么办

官方 codecs 文档列出了标准的错误处理方案，常用的几个：

值官方含义什么时候敢用
"strict"默认。遇到错误就抛异常（UnicodeDecodeError）永远的正解，先让它报错才知道问题在哪
"ignore"忽略无法解码的字节，直接跳过⚠ 会静默丢数据，慎用
"replace"用替代标记（通常是 ? 或 �）替换只是想看看内容、不在乎几个坏字符时
"backslashreplace"替换为反斜杠转义序列，如 \xe9调试时：能看出原始字节是什么
"surrogateescape"把无法解码的字节映射到私有区域码位，可原样写回需要「无损搬运」但暂时解不开内容时

官方文档对 UnicodeEncodeError 给的示例是 '\udc80'.encode('utf-8') 会报错（因为它是代理对码位）。 实际中最常见的还是解码时的 UnicodeDecodeError。

4.7 关键机制五：CSV 的 newline='' 与 Excel 乱码

CSV 不是 Python 发明的，它是一个很老、很松散的格式。Python 的 csv 模块文档里， reader 和 writer 两处都明确写了同一句要求：

如果 csvfile 是一个文件对象，则打开它时应设置 newline=''。 ——引自 Python 标准库 csv 模块文档

为什么？因为 csv 模块要自己处理行结束符。如果你让 Python 的文件层先把 \r\n 转成 \n，

  • 读的时候：可能把字段里的换行符当成记录分隔符，把一行数据拆成两行。
  • 写的时候（Windows）：csv 写出 \r\n，文件层又转一遍，变成 \r\r\n，Excel 打开就多出一堆空行。

所以标准写法是：

with open("data.csv", "r", encoding="utf-8-sig", newline="") as f:
    reader = csv.DictReader(f)
    for row in reader:
        print(row)

注意这个位置：newline="" 是传给 open() 的，不是传给 csv 的。 这是新手最容易传错地方的一个参数。

关于「Excel 打开 CSV 乱码」：

这不是你代码的错。你的程序写出的是正确的 UTF-8 字节；是 Excel 在猜测编码， 而简体中文版 Excel 默认猜 GBK，猜错了就乱码。解决路径有三条：

  1. 最推荐：用 encoding="utf-8-sig" 写出 CSV。那三个 BOM 字节会告诉 Excel「这是 UTF-8」，Excel 就猜对了。代价是给非 Excel 的程序读的时候要注意（用 utf-8-sig 读即可）。
  2. 不写 CSV，直接写 .xlsx（用 openpyxl / pandas），彻底绕开编码猜谜。
  3. 告诉同事：用「数据 → 从文本/CSV 导入」而不是双击打开，手动选 UTF-8。

4.8 关键机制六：二进制模式与性能

官方 io 模块文档指出，文本 I/O 在读写时要做编码/解码，所以文本 I/O 比二进制 I/O 慢得多。 这也是为什么处理图片、音频、压缩包时必须用 "rb" / "wb"：这类数据没有「字符」概念， 强行按文本解码毫无意义，而且会直接抛 UnicodeDecodeError。

官方教程在讨论二进制模式时提醒：二进制模式下，读写的都是 bytes 对象，不会做任何编码转换。 ——引自 Python 官方教程《输入与输出》7.2.1 节

另一个性能要点：读大文件不要 f.read()。

# ❌ 一次性读入内存：文件 2GB，内存 8GB，直接卡死
with open("huge.txt", encoding="utf-8") as f:
    text = f.read()

# ✅ 逐行迭代：内存占用恒定
with open("huge.txt", encoding="utf-8") as f:
    for line in f:
        process(line)

官方明确说文件对象支持迭代，而且是内存高效的做法——它一次只在内存里保留一行。 这是「读大文件」的标准姿势。

4.9 可运行代码：完整对错对比

坑 1：不用 with / 用 with 

# ❌ 忘了 close，且在循环里反复 open 会耗尽文件句柄
f = open("news.txt", "r", encoding="utf-8")
text = f.read()
# 后面如果抛异常，f.close() 永远执行不到

# ✅ with：哪怕中间抛异常也会关
with open("news.txt", "r", encoding="utf-8") as f:
    text = f.read()
print(open("news.txt").closed)  # 只读检查用

坑 2：编码报错的三步排查

# 第一步：先按 utf-8 试，让它把错误说出来
try:
    with open("old.txt", encoding="utf-8") as f:
        print(f.read())
except UnicodeDecodeError as e:
    print("不是 UTF-8：", e)
    # 例：'utf-8' codec can't decode byte 0xd0 in position 0: invalid continuation byte

# 第二步：看到 0xd0 / 0xc0 / 0xb5 这类字节，八成是 GBK 系
with open("old.txt", encoding="gbk") as f:
    print(f.read())

# 第三步：还是不行，用 backslashreplace 看看到底是什么字节
with open("old.txt", encoding="utf-8", errors="backslashreplace") as f:
    print(f.read()[:200])

坑 3：utf-8-sig 与 BOM

import csv

# ❌ 用 utf-8 读 Excel 另存的 CSV：不报错，但列名多了个看不见的 \ufeff
with open("export.csv", encoding="utf-8", newline="") as f:
    reader = csv.DictReader(f)
    for row in reader:
        print(list(row.keys()))
        break
# 输出：['\ufeff标题', '日期', '记者']   ← 注意第一个！

# ✅ 用 utf-8-sig：自动跳过 BOM，有 BOM 无 BOM 都能读
with open("export.csv", encoding="utf-8-sig", newline="") as f:
    reader = csv.DictReader(f)
    for row in reader:
        print(list(row.keys()))
        break
# 输出：['标题', '日期', '记者']

坑 4：CSV 的 newline 与写文件

import csv

rows = [
    ["标题", "日期", "记者"],
    ["某市启动老旧小区改造", "2026-03-01", "李明"],
    ["垃圾分类新规实施首月观察", "2026-03-02", "王芳"],
]

# ❌ 没有 newline=""：Windows 上写出的文件带 \r\r\n，Excel 打开有空行
with open("out1.csv", "w", encoding="utf-8") as f:
    writer = csv.writer(f)
    writer.writerows(rows)

# ✅ 读和写都要 newline=""；写的时候用 utf-8-sig 让 Excel 认得
with open("out2.csv", "w", encoding="utf-8-sig", newline="") as f:
    writer = csv.writer(f)
    writer.writerows(rows)

# 读回来验证
with open("out2.csv", encoding="utf-8-sig", newline="") as f:
    for row in csv.reader(f):
        print(row)

坑 5：'w' 会清空文件

# ❌ 想追加一条新闻，结果把原来 1000 条全删了
with open("news.txt", "w", encoding="utf-8") as f:
    f.write("新的一条\n")

# ✅ 追加用 "a"
with open("news.txt", "a", encoding="utf-8") as f:

坑 6：文件指针位置

with open("news.txt", "r", encoding="utf-8") as f:
    first = f.read(10)     # 读 10 个字符，指针走到第 10 个
    print(f.tell())        # 10
    rest = f.read()        # 从第 10 个往后读，不是从头
    f.seek(0)              # 手动回到开头
    again = f.read(10)     # 又是前 10 个字符
    print(first == again)  # True

坑 8：二进制模式

# ❌ 图片用文本模式打开必然报错

5. 应用场景

场景一：把宣传部发来的 CSV 读进来，做一份简单的选题线索表

现实情况：宣传部或市政热线给你一个 CSV，可能是 Excel 另存的，也可能是老系统导出的。 你要做的第一件事不是分析，而是把它稳稳地读进来——这一步做不对，后面全是白干。 

import csv

def read_clue_table(path):
    """读进来的第一步：探编码 + 读成字典列表。"""
    for enc in ("utf-8-sig", "utf-8", "gbk", "gb18030"):
        try:
            with open(path, encoding=enc, newline="") as f:
                rows = list(csv.DictReader(f))
            print(f"[成功] 用 {enc} 读入 {len(rows)} 条")
            return rows
        except UnicodeDecodeError:
            print(f"[重试] {enc} 不行，换下一个")
    raise RuntimeError("四种编码都试过了，请用记事本另存为 UTF-8")

clues = read_clue_table("热线线索.csv")

# 读进来之后，检查列名有没有 BOM 残留
if clues:
    print("列名：", list(clues[0].keys()))

# 统计各街道的线索条数
from collections import Counter
street_counts = Counter(r["所属街道"] for r in clues if r.get("所属街道"))
for street, n in street_counts.most_common(5):
    print(f"{street}: {n} 条")

这段代码里有三个值得留意的地方：

  • 按顺序试编码：utf-8-sig 放第一个，因为它能兼容有 BOM 和无 BOM 两种情况，命中率最高。
  • newline=""：csv.reader 的行，不能省。
  • 只用 row.get() 读列：某个街道列恰好是空的，直接用 r["所属街道"] 会 KeyError；用 .get() 更稳。

场景二：把舆情统计结果写成一份「Excel 打开不乱码」的报送文件

你要给领导交一份统计表。领导肯定会双击打开看——所以你的任务不是「写对 CSV」， 而是「写出一份双击打开不乱码的 CSV」。 

import csv
from collections import Counter

# 假设 comments = [{"平台": "微博", "情感": "正面"}, ...]
comments = [
    {"平台": "微博", "情感": "正面"},
    {"平台": "微博", "情感": "负面"},
    {"平台": "抖音", "情感": "正面"},
    {"平台": "抖音", "情感": "正面"},
    {"平台": "微信", "情感": "中性"},
]

# 1) 先算出要报送的统计结果
total = len(comments)
counts = Counter((r["平台"], r["情感"]) for r in comments)

# 2) 写出文件：注意 utf-8-sig + newline=""
fieldnames = ["平台", "情感", "条数", "占比"]
with open("舆情日报_20260917.csv", "w", encoding="utf-8-sig", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=fieldnames)
    writer.writeheader()
    for (platform, sentiment), n in sorted(counts.items()):
        writer.writerow({
            "平台": platform,
            "情感": sentiment,
            "条数": n,
            "占比": f"{n / total:.1%}",     # 1.2% 这种格式
        })

print("已写出，双击用 Excel 打开验证是否乱码")

关键在这两处：

  • encoding="utf-8-sig"：给 Excel 一个明确的 UTF-8 信号，乱码问题基本消失。
  • newline=""：Windows 上不加，Excel 打开会看到「每两行数据之间夹一个空行」。

最后一步永远是：自己双击打开看一眼。这不是多余的，是交付前的必要动作。

6. 概念辨析

辨析 1：open() 不写 encoding vs 写 encoding

# ❌ 不写 encoding：平台相关，Windows 中文系统默认 GBK
with open("data.txt") as f:
    text = f.read()

# ✅ 显式指定：跨平台一致
with open("data.txt", encoding="utf-8") as f:
    text = f.read()

官方在 io 文档里的原话是「强烈建议你在打开文本文件时显式地指定编码格式」。 不写的代码在你自己电脑上能跑，在别人电脑上可能就报 UnicodeDecodeError。 这不是风格偏好，是可移植性要求。

辨析 2：utf-8 vs utf-8-sig

import csv
# 假设 export.csv 是 Excel「另存为 CSV UTF-8」导出的，带 BOM

# ❌ utf-8：不报错，但列名第一个字符是 \ufeff
with open("export.csv", encoding="utf-8", newline="") as f:
    print(list(next(csv.DictReader(f)).keys()))
# ['\ufeff标题', '日期']

# ✅ utf-8-sig：自动跳过 BOM
with open("export.csv", encoding="utf-8-sig", newline="") as f:
    print(list(next(csv.DictReader(f)).keys()))
# ['标题', '日期']

记忆点：utf-8-sig = utf-8 + 「写的时候加 BOM，读的时候跳过 BOM」。 读别人的文件用 utf-8-sig 更稳；写 CSV 给 Excel 看也用 utf-8-sig； 写 JSON、代码、给程序读的文件用纯 utf-8。

辨析 3：errors="ignore" vs 「找到正确编码」

# ❌ 用 ignore 让报错消失，但数据被静默丢掉，而且你永远不知道丢了什么
with open("old.txt", encoding="utf-8", errors="ignore") as f:
    text = f.read()      # 不报错，但有些字变成了空气

# ✅ 先搞清楚它是什么编码，再正确读取
with open("old.txt", encoding="gbk") as f:
    text = f.read()

errors="ignore" 最大的问题是它让错误变得不可见。 你以为读进来了 1000 条数据，其实有 30 条里的字被悄悄删了——做舆情统计时，这就是数据失真。 只在「我只是想大概看一眼这是什么文件」时才允许用。

辨析 4：with vs 手动 close()

# ❌ 手动关：中间一抛异常，close 就永远执行不到
f = open("news.txt", encoding="utf-8")
data = f.read()
x = 1 / 0          # 抛 ZeroDivisionError
f.close()          # 永远到不了这一行

# ✅ with：异常时也保证关闭
with open("news.txt", encoding="utf-8") as f:
    data = f.read()
    x = 1 / 0      # 抛异常，但文件一定被关了

只有当文件对象的生命周期跨函数、无法用 with 包住时才考虑手动管理。 日常写脚本，with 是唯一正解。

辨析 5：文本模式 "r" vs 二进制模式 "rb"

# 文本模式：读到 str，会自动做编码转换和换行符转换
with open("news.txt", "r", encoding="utf-8") as f:
    print(type(f.read()))     # <class 'str'>

# 二进制模式：读到 bytes，不做任何转换
with open("news.txt", "rb") as f:
    b = f.read()
    print(type(b))            # <class 'bytes'>
    print(b[:20])             # b'\xe6\x9f\x90\xe5\xb8\x82...'

判据很简单：这份文件里有「文字」吗？有就用文本模式；没有（图片、音频、视频、压缩包）就用二进制模式。 另外官方提到文本 I/O 比二进制 I/O 慢很多，如果你在做大规模的数据处理且不需要解码，可以考虑二进制模式。

辨析 6：w vs a

# "w"：清空原内容，从头写
with open("log.txt", "w", encoding="utf-8") as f:
    f.write("今天第一条\n")
# 文件内容：今天第一条

# "a"：在原内容末尾追加
with open("log.txt", "a", encoding="utf-8") as f:
    f.write("今天第二条\n")
# 文件内容：今天第一条 / 今天第二条

做每日抓取日志、增量收集数据时，一律用 "a"。 用 "w" 跑一次循环，昨天抓的数据就全没了——这是真实会发生的生产事故。

7. 自测问题

Q1：下面这段代码跑完，data.csv 里还剩几行？为什么？ 
with open("data.csv", "w", encoding="utf-8") as f:
    f.write("a,b\n")
只剩 1 行。因为 "w" 模式会先清空文件原有内容再写。 如果你的本意是追加，应该用 "a"。这个坑做数据收集时最致命。
Q2：报错 UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd0 in position 0: invalid continuation byte，你的排查顺序是什么？
① 确认这是解码问题，不是代码逻辑问题——你的代码没写错，是文件的编码不是 UTF-8； ② 尝试 encoding="gbk"（0xd0 这种高位字节是 GBK 系的典型特征）； ③ 还不行就试 gb18030，再不行用 errors="backslashreplace" 打出前几百字节看规律； ④ 实在搞不定，用记事本/VSCode 打开「另存为 UTF-8」，一劳永逸。
Q3：用 encoding="utf-8" 读 Excel 另存的 CSV，程序没报错，但 row["标题"] 抛 KeyError: '标题'。为什么？
因为文件带 BOM。前三个字节 0xef 0xbb 0xbf 被当成了一个字符 \ufeff， 拼到了第一列列名前面，实际列名是 '\ufeff标题'。 它零宽不可见，所以 print 出来看着一模一样。 改用 encoding="utf-8-sig"，或者用 print(repr(列名)) 亲自确认一下。
Q4：读写 CSV 时 newline='' 应该加在哪儿？不加会怎样？
加在 open() 的参数里，不是 csv.reader() 里。 不加的话：读的时候字段内的换行可能被误当成记录分隔；写的时候（Windows）会写出 \r\r\n， 用 Excel 打开会看到每行数据之间多一个空行。
Q5：同事说「你写的 CSV 用 Excel 打开是乱码」。你的代码有问题吗？怎么回应？
大概率代码没问题。你写的是正确的 UTF-8 字节，是 Excel 在猜编码，简体中文版 Excel 默认猜 GBK。 三种处理方式：① 写出时改用 encoding="utf-8-sig"，用 BOM 告诉 Excel 这是 UTF-8（最推荐）； ② 直接输出 .xlsx 文件；③ 让对方用「数据 → 从文本/CSV 导入」并手动选 UTF-8。
Q6：为什么处理图片时 open("a.jpg", encoding="utf-8") 一定会失败？
因为默认是文本模式 "r"，Python 会尝试把文件内容按 UTF-8 规则解码成 str。 而 JPEG 里是一堆随机的二进制字节，几乎必然包含不合法的 UTF-8 序列。 正确做法是 open("a.jpg", "rb")，拿到 bytes，不做任何解码。
Q7：官方为什么不推荐在 UTF-8 文件里使用 BOM？但你又为什么有时候必须用 utf-8-sig？
官方原话是「在 UTF-8 中并不推荐使用 BOM，通常应当避免它们的出现」—— 因为 BOM 是 Microsoft 为兼容旧软件发明的，它不是 UTF-8 标准的一部分，会给其它程序解析带来麻烦。 但现实是 Excel 靠这三个字节来正确识别 UTF-8 而不乱码， 所以「给 Excel 看的 CSV」用 utf-8-sig，「给程序和工具看的文件」用纯 utf-8。

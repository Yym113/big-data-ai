1. 个人理解（先说人话）

零基础同学最怕的东西就是那一大段红字报错。看到 Traceback (most recent call last): 就想关掉窗口。但这一节想告诉你两件事：

第一，那一大段红字不是「你完了」，它是一份地图。 它精确地告诉你：哪一行出错、调用链是什么、错误类型是什么。 读懂它，比读懂代码还重要——因为代码是你写的，你大概记得；报错信息是你没见过的，它才是新信息。

第二，异常处理不是「让报错消失」，而是「让报错在你能控制的地方发生」。 新手最常见的做法是把整个程序包进 try: ... except: pass， 这样报错确实消失了——但你的程序也变成了一台「什么都说好的机器」： 数据读失败它不说、账号登不上它不说、抓了 0 条它也不说， 最后你拿着一个空结果去交差，还以为一切正常。

记住一句话：except: pass 是给自己埋的雷。 今天你把错误吞了，明天你会花三小时找一个本可以在三秒内被报错告诉你的问题。

官方文档对这一点的表述是：Exception 可以被用作通配符，「捕获（几乎）一切」， 但「好的做法是，尽可能具体地说明我们打算处理的异常类型，并允许任何意外的异常传播下去」。

2. 学习目标

学完这一份，你应该能做到：

  • 能区分语法错误（SyntaxError，程序根本没开始跑）和异常（程序跑到一半崩了）。
  • 能从下往上读 Traceback：最后一行是「什么错」，上面是「在哪出错」，再往上是「谁调用了它」。
  • 能默写 try / except / else / finally 四件套，并说清每一部分分别在什么时候执行。
  • 能看懂并说出 10 种以上常见异常的中文含义（TypeError、ValueError、KeyError、IndexError、FileNotFoundError、ModuleNotFoundError 等）。
  • 能解释为什么 except: pass 是坏习惯，并知道该怎么改（具体异常 + 记录日志 + 必要时 raise）。
  • 能说出 finally 的核心性质：不论是否发生异常都会执行，以及它适合做什么（释放资源）。
  • 会用 raise 主动抛异常、用 raise ... from exc 保留异常链。
  • 知道可以自定义异常类，且应该从 Exception 派生。

3. 核心问题清单

  1. 语法错误和异常有什么区别？为什么说「语法错误程序根本没跑起来」？
  2. Traceback 那一大段，应该从哪一行开始读？为什么它写「most recent call last」？
  3. Traceback 里箭头 ^^^^ 指向的位置一定就是错的地方吗？
  4. try 子句里如果抛了异常，剩余的语句还会执行吗？
  5. 多个 except 子句，会有几个被执行？匹配顺序重要吗？
  6. else 子句是干什么的？「不加也行」为什么官方说加了更好？
  7. finally 到底在什么时候执行？它和 except 谁先谁后？
  8. 为什么 except: pass 危险？如果我就是想「出错就跳过」该怎么办？
  9. except Exception 和裸 except: 差在哪？
  10. KeyboardInterrupt 和 SystemExit 为什么不该被捕获？
  11. 函数里 try 调用了另一个函数，那个函数里出的错，外面的 except 能接住吗？
  12. raise 单独一句（不带参数）是什么意思？
  13. 「异常链」是什么？raise ... from exc 和 from None 各解决什么问题？
  14. 自定义异常为什么要从 Exception 而不是 BaseException 派生？

4. 结构化解释

4.1 定义：错误分两种

官方教程《错误和异常》开头就分了类：

错误可（至少）被分为两种：语法错误 和 异常。 ——引自 Python 官方教程《错误和异常》开头

语法错误（SyntaxError，又称解析错误）：程序连「开始执行」这一步都没走到。

>>> while True print('Hello world')
  File "<stdin>", line 1
    while True print('Hello world')
               ^^^^^
SyntaxError: invalid syntax

官方对这段报错有一段非常值得记住的说明：

解析器会重复出错的行并显示指向检测到错误的位置的小箭头。 请注意这并不一定是需要被修复的位置。 在这个例子中，错误在 print() 上被检测到，原因则是在它之前缺少一个冒号（':'）。 ——引自 Python 官方教程《错误和异常》8.1 节

这一句解释了新手最大的困惑之一：「它指着 print，但 print 明明没错啊！」 因为解析器是读到那儿才发现前面不对。所以看到 SyntaxError， 眼睛要往回看，尤其看看上一行结尾是不是少了冒号、括号是不是没配平。

异常（Exception）：语法没问题，程序跑起来了，跑到某一步崩了。

>>> 10 * (1/0)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    10 * (1/0)
          ~^~
ZeroDivisionError: division by zero

官方对此的说明：

错误信息的最后一行说明程序遇到了什么类型的错误。……此行其余部分根据异常类型，结合出错原因，说明错误细节。
错误信息开头用堆栈回溯形式展示发生异常的语境。 ——引自 Python 官方教程《错误和异常》8.2 节

4.2 最小模型：Traceback 是一份「事故调查报告」

把 Traceback 想象成一份交通事故报告。它记录的是「事故是怎么一步步发生的」：

  • 最后一行 = 结论：出了什么事故（异常类型 : 具体原因）。
  • 最下面的 File 行 = 事故现场：最后出错的那一行代码在哪个文件第几行。
  • 上面的 File 行 = 事故经过：是谁把程序执行带到这一步的。
Traceback (most recent call last):
  File "report.py", line 12, in <module>      ← 第 3 步：module（主程序）第 12 行调用了
    summarize(data)
  File "report.py", line 6, in summarize       ← 第 2 步：summarize 函数第 6 行调用了
    total = sum(int(x) for x in data)
  File "report.py", line 6, in <genexpr>       ← 第 1 步：这里真正炸了
    total = sum(int(x) for x in data)
ValueError: invalid literal for int() with base 10: '暂无'   ← 结论

读法：从最后一行开始，往上找第一个「你写的代码」。

「most recent call last」的意思是「最近一次调用在最后」， 也就是越往下越接近事故发生的那一刻。所以从下往上读，才是从结果倒推到原因。 新手常犯的错是从上往下读，结果读到的是「程序一开始的地方」，跟问题无关。

现实类比Traceback 里对应什么
事故结论：追尾ValueError: ...（异常类型 + 原因）
事故现场：某路口最下面那个 File "x.py", line N
行车记录：怎么开到这个路口的上面那些 File 行（调用链）
地面标线指示的碰撞点^^^^ 小箭头
实用技巧：Traceback 很长时，用手指压住屏幕最下面，从那一行往上读， 找到第一个文件名是你自己写的文件（不是 Python 库里的文件）的那一行。那儿就是你的战场。

4.3 关键机制一：try 语句的工作原理

官方给出了非常清晰的四步说明：

  • 首先，执行 try 子句（try 和 except 关键字之间的（多行）语句）。
  • 如果没有触发异常，则跳过 except 子句，try 语句执行完毕。
  • 如果在执行 try 子句时发生了异常，则跳过该子句中剩下的部分。如果异常的类型与 except 关键字后指定的异常相匹配，则会执行 except 子句，然后跳到 try/except 代码块之后继续执行。
  • 如果发生的异常与 except 子句中指定的异常不匹配，则它会被传递到外层的 try 语句中；如果没有找到处理器，则它是一个 未处理异常 且执行将停止并输出一条错误消息。
——引自 Python 官方教程《错误和异常》8.3 节

官方给的第一个例子（要求用户持续输入直到输入有效整数）：

while True:
    try:
        x = int(input("Please enter a number: "))
        break
    except ValueError:
        print("Oops!  That was no valid number.  Try again...")

注意第二点「跳过该子句中剩下的部分」—— 这意味着如果 try 里有三行，第二行抛异常了，第三行永远不会执行，直接跳到 except。 很多新手以为 try 里的代码「出错了就重试」，不是的，是把剩下的跳过去。

4.4 关键机制二：多个 except 与匹配顺序

官方原文：

一条 try 语句可以有多个 except 子句，以便为不同的异常指定处理器。 但最多只有一个处理器会被执行。处理器只处理对应 try 子句 中发生的异常， 而不处理同一 try 子句内其他处理器中的异常。

一个 except 子句中的类匹配的异常将是该类本身的实例或其所派生的类的实例 （但反过来则不可以 --- 列出派生类的 except 子句 不会匹配其基类的实例）。 ——引自 Python 官方教程《错误和异常》8.3 节

官方给的顺序影响结果的例子：

class B(Exception):
    pass

class C(B):
    pass

class D(C):
    pass

for cls in [B, C, D]:
    try:
        raise cls()
    except D:
        print("D")
    except C:
        print("C")
    except B:
        print("B")

官方说明：上面的代码将依次打印 B, C, D；

请注意如果颠倒 except 子句 的顺序（把 except B 放在最前）， 则会输出 B, B, B --- 即触发了第一个匹配的 except 子句。 ——引自 Python 官方教程《错误和异常》8.3 节

实践结论：把具体的异常写前面，笼统的写后面。 FileNotFoundError 要写在 OSError 前面， ModuleNotFoundError 要写在 ImportError 前面， Exception 放最后兜底。

绑定异常实例、以及官方推荐的「打印后重新抛出」模式：

import sys

try:
    f = open('myfile.txt')
    s = f.readline()
    i = int(s.strip())
except OSError as err:
    print("OS error:", err)
except ValueError:
    print("Could not convert data to an integer.")
except Exception as err:
    print(f"Unexpected {err=}, {type(err)=}")
    raise

这一段是官方给出的「最常见的处理模式」。注意最后两行： 兜底的 except Exception 不是吞掉，而是打印出来然后 raise 继续往上抛。 这才是「记录 + 不掩盖」的正确姿势。

关于异常实例的属性，官方还有一个例子：

>>> try:
...     raise Exception('spam', 'eggs')
... except Exception as inst:
...     print(type(inst))    # 异常的类型
...     print(inst.args)     # 参数保存在 .args 中
...     print(inst)          # __str__ 允许 args 被直接打印
...     x, y = inst.args     # 解包 args
...     print('x =', x)
...     print('y =', y)

4.5 关键机制三：else 子句

官方说明：

try ... except 语句具有可选的 else 子句， 该子句如果存在，它必须放在所有 except 子句 之后。 它适用于 try 子句 没有引发异常但又必须要执行的代码。

使用 else 子句比向 try 子句添加额外的代码要好， 可以避免意外捕获非 try ... except 语句保护的代码触发的异常。 ——引自 Python 官方教程《错误和异常》8.3 节

官方示例：

for arg in sys.argv[1:]:
    try:
        f = open(arg, 'r')
    except OSError:
        print('cannot open', arg)
    else:
        print(arg, 'has', len(f.readlines()), 'lines')
        f.close()

为什么 else 比「把代码都塞进 try」好？看这个对比： 

# ❌ 把处理逻辑也放进 try：如果 process() 里出 ValueError，会被下面的 except 吞掉
try:
    f = open("data.csv")
    result = process(f.read())     # 这里的 ValueError 也会被当成「打开文件失败」
except OSError:
    print("打开文件失败")
    print("打开失败")

# ✅ 用 else：try 里只放「可能失败的那一件事」
try:
    f = open("data.csv")
except OSError:
    print("打开文件失败")
else:
    result = process(f.read())     # 这里的异常不会被上面的 except 收走
    f.close()

一句话记忆：try 里只放「你明确知道可能抛什么异常」的代码， 其余的都放 else。 这样 except 才不会误伤。

4.6 关键机制四：finally 与清理操作

官方对 finally 的定义非常明确：

try 语句还有一个可选子句，用于定义在所有情况下都必须要执行的清理操作。

如果存在 finally 子句，则 finally 子句是 try 语句结束前执行的最后一项任务。 不论 try 语句是否触发异常，都会执行 finally 子句。 ——引自 Python 官方教程《错误和异常》8.7 节

官方给出了几种「比较复杂的情景」，逐条列在这里，因为它们解释了几乎所有关于 finally 的困惑：

  • 如果 try 子句触发了异常，某个 except 应处理它；如果没人处理，会在 finally 执行后被重新触发。
  • except 或 else 子句执行期间也会触发异常，同样会在 finally 之后被重新触发。
  • 如果 finally 里执行了 break、continue 或 return，异常不会被重新引发—— 官方说「这可能会引起混淆，因此不鼓励使用」，从 3.14 起编译器会发出 SyntaxWarning（PEP 765）。
  • 如果 try 里遇到 break/continue/return，finally 会在这些语句之前执行。
  • 如果 finally 里有 return，返回值将是 finally 里的那个 return，而不是 try 里的—— 官方同样说「这可能会引起混淆，因此不提倡使用」。

官方那个经典示例：

>>> def bool_return():
...     try:
...         return True
...     finally:
...         return False
...
>>> bool_return()
False

以及 divide 那个例子，把四种情况跑了一遍：

def divide(x, y):
    try:
        result = x / y
    except ZeroDivisionError:
        print("division by zero!")
    else:
        print("result is", result)
    finally:
        print("executing finally clause")

divide(2, 1)      # result is 2.0 / executing finally clause
divide(2, 0)      # division by zero! / executing finally clause
divide("2", "1")  # executing finally clause，然后抛 TypeError

注意 divide("2", "1")：except ZeroDivisionError 接不住 TypeError， 所以程序先打印了 finally 那句话，然后让 TypeError 冒出去。 这就是「finally 一定执行，异常该冒还是冒」的实证。

官方对 finally 的用途总结：

在实际应用程序中，finally 子句对于释放外部资源（例如文件或者网络连接）非常有用， 无论是否成功使用资源。 ——引自 Python 官方教程《错误和异常》8.7 节

而在 Python 里，这件事有更好的写法——with。 官方在 8.8 节「预定义的清理操作」说得很直白：

语句执行完毕后，即使在处理行时遇到问题，都会关闭文件 f。 ——引自 Python 官方教程《错误和异常》8.8 节 
# 手动管理：啰嗦，且容易漏
f = open("news.txt")
try:
    for line in f:
        print(line, end="")
finally:
    f.close()

# with：一样的效果，一行搞定
with open("news.txt") as f:
    for line in f:
        print(line, end="")

所以实践结论是：能用 with 就用 with；真的没有 with 支持时才用 finally。

4.7 关键机制五：raise 与异常链

官方的 raise 说明：

raise 唯一的参数就是要触发的异常。这个参数必须是异常实例或异常类（派生自 BaseException 类，例如 Exception 或其子类）。 如果传递的是异常类，将通过调用没有参数的构造函数来隐式实例化。 ——引自 Python 官方教程《错误和异常》8.4 节 
raise ValueError          # 等价于 raise ValueError()
raise ValueError("年龄不能是负数")   # 带上说明信息（推荐）

# 只想「标记一下」但不想处理，用不带参数的 raise 重新抛出
try:
    raise NameError('HiThere')
except NameError:
    print('An exception flew by!')
    raise        # 原样再抛出去

异常链——这是很多人不知道但很有用的一块。官方说明：

如果一个未处理的异常发生在 except 部分内，它将会有被处理的异常附加到它上面，并包括在错误信息中。

为了表明一个异常是另一个异常的直接后果，raise 语句允许一个可选的 from 子句。 转换异常时，这种方式很有用。 ——引自 Python 官方教程《错误和异常》8.5 节 
def func():
    raise ConnectionError

try:
    func()
except ConnectionError as exc:
    raise RuntimeError('Failed to open database') from exc

这样 Traceback 会明确告诉你两件事的因果关系：

ConnectionError

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  ...
RuntimeError: Failed to open database

还有 from None，用来主动切断这条链：

try:
    open('database.sqlite')
except OSError:
    raise RuntimeError from None
# Traceback 里只剩 RuntimeError，不再显示那个 FileNotFoundError

什么时候用哪个？ 写库 / 写给别人用的模块时，raise ... from exc 能让使用者看到完整因果； 而当你把「底层技术细节」转换成「面向业务的错误」且不想暴露细节时，才用 from None。

4.8 关键机制六：自定义异常

官方的说法：

程序可以通过创建新的异常类命名自己的异常。不论是以直接还是间接的方式，异常都应从 Exception 类派生。

异常类可以被定义成能做其他类所能做的任何事，但通常应当保持简单， 它往往只提供一些属性，允许相应的异常处理程序提取有关错误的信息。

大多数异常命名都以"Error"结尾，类似标准异常的命名。 ——引自 Python 官方教程《错误和异常》8.6 节

在 exceptions 模块文档的前言里还有一句很关键的提醒：

鼓励程序员从 Exception 类或其子类派生新异常，而不是从 BaseException 派生。 ——引自 Python 标准库 exceptions 模块文档前言

为什么？因为 BaseException 下面挂了 SystemExit、KeyboardInterrupt、GeneratorExit 这三个「控制流信号」。 它们不是错误，而是「程序该退出了」的通知。如果你从 BaseException 派生， 那些「except Exception 兜底」的代码就接不住你的异常，行为会很怪。

实践里最简写法：

class DataFormatError(Exception):
    """当输入数据的列名不符合预期时抛出。"""
    pass

class FetchError(Exception):
    def __init__(self, url, status_code):
        self.url = url
        self.status_code = status_code
        super().__init__(f"{url} 返回 {status_code}")

try:
    raise FetchError("https://example.com/news", 503)
except FetchError as e:
    print(e.status_code, e.url)
类名一律用英文。上面的写法在 Python 里语法合法，也很直观， 但中文标识符在团队协作、日志检索、和第三方库混用时会有麻烦。 建议类名用英文（如 FetchError、SchemaError）， 异常信息用中文（如 raise FetchError("页面返回 503")）。

4.9 关键机制七：常见异常类型对照表

下表按「你会在什么时候见到它」组织。定义措辞以官方 exceptions 模块文档为准。

异常官方定义（节译 / 引言）你会在什么时候见到它
Exception 所有内置的非系统退出类异常的基类；所有用户自定义异常也应从它派生 兜底 except 的默认选择
SyntaxError 解析器遇到语法错误时抛出 少冒号、少括号、少逗号
IndentationError 与不正确缩进有关的语法错误的基类（SyntaxError 的子类） 缩进乱了
TabError 缩进中 Tab 和空格混用不一致时抛出（IndentationError 的子类） 从网页或 Word 复制代码
NameError 找不到局部或全局名称时抛出（仅适用于未限定名称） 变量名拼错、变量还没赋值
UnboundLocalError 引用了函数或方法里的局部变量，但该变量尚未绑定任何值（NameError 的子类） 函数里给变量赋值了，又想在赋值前读它
TypeError 对类型不合适的对象应用了操作或函数 "1" + 1、参数个数不对
ValueError 操作或函数收到了类型正确但值不合适的参数 int("暂无")、int("12abc")
AttributeError 属性引用或赋值失败时抛出 "abc".push、对象没有这个方法
IndexError 序列下标超出范围时抛出（切片下标会被静默截断到有效范围；下标不是整数则抛 TypeError） [1,2,3][10]
KeyError 在现有键的集合中找不到映射（字典）键时抛出 d["不存在的键"]
ZeroDivisionError 除法或取模运算的第二个参数为零时抛出 1/0、算占比时分母为 0
FileNotFoundError 请求的文件或目录不存在时抛出（对应 errno 的 ENOENT） 路径写错、换个电脑跑
PermissionError 在没有足够访问权限的情况下尝试运行操作时抛出（如文件系统权限；对应 EACCES、EPERM） 文件被 Excel 占用、无写权限
ModuleNotFoundError ImportError 的子类，import 找不到模块时抛出 没装包、装到了别的虚拟环境
ImportError import 语句加载模块出问题时抛出；from ... import 的名字找不到时也抛 包名拼错、包内部缺依赖
UnicodeDecodeError 解码期间发生 Unicode 相关错误时抛出（UnicodeError 的子类，而 UnicodeError 是 ValueError 的子类） 用错编码读中文文件
StopIteration 由内置函数 next() 和迭代器的 __next__() 方法抛出，表示迭代器不再产生更多项目 手动驱动迭代器时；生成器里不该主动抛它
RecursionError 解释器检测到超过最大递归深度时抛出（RuntimeError 的子类） 递归忘了写终止条件
RuntimeError 检测到不属于任何其它类别的错误时抛出 各种「不属于别的类别」的运行时问题
KeyboardInterrupt 用户按下中断键（通常是 Control-C）时抛出；它继承自 BaseException，以免被捕获 Exception 的代码意外捕获而导致解释器无法退出 你按了 Ctrl+C
AssertionError assert 语句失败时抛出 自检断言不成立
OSError 系统函数返回系统相关错误时抛出，包括「文件不存在」或「磁盘已满」等 I/O 失败 文件系统的各种问题；是 FileNotFoundError、PermissionError 的父类

官方 TypeError 与 ValueError 的分工，有一段很精辟的说明值得单独抄下来：

传入错误类型的参数（例如在期望 int 时传入了 list）应当导致 TypeError， 而传入错误值的参数（例如超出预期边界的数字）应当导致 ValueError。 ——引自 Python 标准库 exceptions 模块文档 TypeError 条目

类型不对 → TypeError；类型对但值不对 → ValueError。 这一句能解决八成的选择困难。

4.10 关键机制八：继承层次结构

把下面这棵树记住主干，前面表格里的所有「为什么接不住/接住了」就都能推理出来：

BaseException
 ├── BaseExceptionGroup
 ├── GeneratorExit
 ├── KeyboardInterrupt          ← 直接继承 BaseException
 ├── SystemExit                 ← 直接继承 BaseException
 └── Exception
      ├── ArithmeticError
      │    ├── FloatingPointError
      │    ├── OverflowError
      │    └── ZeroDivisionError
      ├── AssertionError
      ├── AttributeError
      ├── EOFError
      ├── ImportError
      │    └── ModuleNotFoundError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── NameError
      │    └── UnboundLocalError
      ├── OSError
      │    ├── FileNotFoundError
      │    ├── PermissionError
      │    └── ...
      ├── RuntimeError
      │    ├── NotImplementedError
      │    └── RecursionError
      ├── StopIteration
      ├── SyntaxError
      │    └── IndentationError
      │         └── TabError
      ├── TypeError
      └── ValueError
           └── UnicodeError
                ├── UnicodeDecodeError
                └── UnicodeEncodeError

依据 Python 标准库 exceptions 模块文档「异常层次结构」一节整理，为便于阅读省略了部分节点。

三个可以直接从树上看出来的结论：

  • except OSError 能接住 FileNotFoundError 和 PermissionError（它们是子类）。
  • except Exception 接不住 KeyboardInterrupt（它不挂在 Exception 下面）。这是故意设计的。
  • except ValueError 能接住 UnicodeDecodeError——因为 UnicodeError 是 ValueError 的子类。这一点很多人不知道。

4.11 可运行代码：完整对错对比

坑 1：裸 except + pass（最严重）

# ❌ 灾难级写法：任何错误都被吞掉，包括 Ctrl+C
def read_data(path):
    try:
        with open(path, encoding="utf-8") as f:
            return f.read()
    except:
        pass          # 什么都没发生，返回 None

# 结果：路径写错、编码不对、权限不够……全都静默变成 None
# 你在下游处理 None 时才崩，而那里离真正的原因已经很远了

# ✅ 只捕你知道会出什么问题，并且如实记录
import logging

def read_data(path):
    try:
        with open(path, encoding="utf-8") as f:
            return f.read()
    except FileNotFoundError:
        logging.error("文件不存在：%s", path)
        raise                       # 抛给调用者决定怎么办
    except UnicodeDecodeError as e:
        logging.error("编码不对：%s（%s）", path, e)
        raise

坑 2：except Exception vs 裸 except:

# ❌ 裸 except：连 KeyboardInterrupt / SystemExit 都抓，Ctrl+C 按不死
try:
    长循环()
except:
    print("出错了")

# ✅ except Exception：不抓 KeyboardInterrupt / SystemExit
try:
    长循环()
except Exception as e:
    print(f"出错了：{e!r}")

官方在 KeyboardInterrupt 条目里解释了为什么它继承自 BaseException： 「以免被捕获 Exception 的代码意外捕获而导致解释器无法退出」。 所以裸 except: 的后果很具体：你的程序会变得按 Ctrl+C 也停不掉。

坑 3：except 顺序颠倒导致接错

# ❌ OSError 写在前面：FileNotFoundError 永远轮不到自己的处理器
try:
    read_data("不存在的文件.csv")
except OSError:
    print("文件系统问题")        # 被这里接走了
except FileNotFoundError:
    print("文件不存在")          # 死代码，永不执行

# ✅ 具体的写前面
try:
    read_data("不存在的文件.csv")
except FileNotFoundError:
    print("文件不存在")
except PermissionError:
    print("没有权限")
except OSError:
    print("其它文件系统问题")

坑 4：把处理逻辑塞进 try，被 except 误伤

# ❌ 分母为 0 的错误也被算成「数据格式不对」
try:
    rows = 读CSV("a.csv")
    ratio = len(rows) / 0
except ValueError:
    print("数据格式不对")     # 会在这里报错？不，ZeroDivisionError 接不住，直接崩

# 更糟的是这种：业务逻辑的 ValueError 被当成「读文件失败」
try:
    rows = 读CSV("a.csv")
    title = rows[0][0].strip()
    if int(title) < 0:        # 这里的 ValueError 会被下面的 except 吞掉
        pass
except ValueError:
    print("读文件失败")       # 误导性极强的错误信息

# ✅ try 里只放可能失败的那一件事
try:
    rows = 读CSV("a.csv")
except ValueError:
    print("读文件失败")
else:
    title = rows[0][0].strip()
    # 后续逻辑放在 else 里，异常语义清晰

坑 5：finally 里有 return（会吃掉异常）

# ❌ finally 里 return，异常被静默吞掉
def lookup_score(name):
    try:
        return db[name]
    finally:
        return -1       # 无论发生什么，永远返回 -1；KeyError 也不见了！

print(lookup_score("不存在"))   # -1，你完全不知道出了问题

# ✅ finally 只做清理，不做返回
def lookup_score(name):
    try:
        return db[name]
    finally:
        print(f"[日志] 查询 {name} 完成")    # 只做记录/清理

官方对这个行为的原话是：「如果一个 finally 子句包含一个 return 语句， 返回的值将是来自 finally 子句的 return 语句，而不是来自 try 子句的 return 语句。 这可能会引起混淆，因此不提倡使用。」

坑 6：用 try/except 代替本该有的判断

# ❌ 用异常来控制正常流程：读 10000 个字典的键，抛 9999 次异常，很慢
for row in rows:
    try:
        v = row["来源"]
    except KeyError:
        v = "未知"

# ✅ 用 .get() 表达「可能没有」的语义，更快也更清楚
for row in rows:
    v = row.get("来源", "未知")

原则：异常是给「意外情况」用的，不是给「预期内的情况」用的。 键可能不存在，这是预期内的，用 .get()；文件可能读不到，这是意外，用 try。

坑 7：记不住异常类型时盲目试错

# ❌ 一排 except 猜类型，看到哪个生效就留哪个
try:
    x = int("12abc")
except ValueError:
    print("A")
except TypeError:
    print("B")
except Exception:
    print("C")

# ✅ 在 REPL 里跑一次，让 Python 告诉你答案
# >>> int("12abc")
# ValueError: invalid literal for int() with base 10: '12abc'
# 然后就精确地写 except ValueError

坑 8：主动 raise 时丢掉原始信息

# ❌ 重新抛一个不含原因的新异常，原始现场全丢了
try:
    fetch(url)
except Exception:
    raise RuntimeError("抓取失败")     # 为什么失败？不知道了

# ✅ 用 from 保留因果链
try:
    fetch(url)
except Exception as exc:
    raise RuntimeError(f"抓取失败：{url}") from exc

# 如果确实不想暴露底层细节（比如给外部用户看），显式切断
try:
    fetch(url)
except Exception:
    raise RuntimeError("服务暂时不可用") from None

坑 9：自定义异常从 BaseException 派生

# ❌ 从 BaseException 派生：except Exception 接不住它
class MyError(BaseException):
    pass

try:
    raise MyError()
except Exception:
    print("接不住")     # 不会执行，程序直接崩

# ✅ 从 Exception 派生
class MyError(Exception):
    pass

坑 10：完整四件套的正确用法

import csv
import logging

def read_clue_table(path):
    """四件套都在的例子：try 只做可能失败的事，else 做后续，finally 记录。"""
    f = None
    try:
        f = open(path, encoding="utf-8-sig", newline="")
    except FileNotFoundError:
        logging.error("文件不存在：%s", path)
        raise
    else:
        # 只有打开成功才走到这里
        rows = list(csv.DictReader(f))
        return rows
    finally:
        # 不论成功失败都执行：这里手动关（实际项目请直接用 with）
        if f is not None:
            f.close()

5. 应用场景（新闻传播学）

场景一：批量抓取稿件时，让「个别失败」不影响整体，但要留下记录

真实场景：你要抓 200 个页面的标题做一个监测。现实是——有的页面 404，有的超时， 有的返回的内容结构变了。你不可能因为第 37 个页面失败就放弃后面 163 个。 但你也绝不能把失败悄悄吞掉，因为「抓到了 163 条」和「有 37 条失败了」 必须在报告里说清楚。 

import logging
from urllib.request import urlopen

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)

class FetchError(Exception):
    """抓取过程中的可预期失败（网络/状态码/结构变化）。"""
    def __init__(self, url, reason):
        self.url = url
        self.reason = reason
        super().__init__(f"{url} —— {reason}")


def fetch_title(url):
    try:
        with urlopen(url, timeout=10) as resp:
            html = resp.read().decode("utf-8", errors="replace")
    except TimeoutError as exc:
        raise FetchError(url, "超时") from exc
    except OSError as exc:
        raise FetchError(url, f"网络错误：{exc}") from exc

    # 结构可能变了，用一个明确的检查代替「裸 except」
    if "<title>" not in html:
        raise FetchError(url, "页面结构不符合预期")
    return html.split("<title>")[1].split("</title>")[0]


url_list = [f"https://example.com/news/{i}" for i in range(1, 201)]

ok, failed = [], []
for url in url_list:
    try:
        title = fetch_title(url)
    except FetchError as exc:
        failed.append((url, exc.reason))
        logging.warning("抓取失败：%s", exc)     # 留痕，但不中断
    else:
        ok.append((url, title))

print(f"成功 {len(ok)} 条，失败 {len(failed)} 条")
# 把失败清单也写出来，交报告时一起附上
for url, reason in failed[:5]:
    print("  ", url, "→", reason)

这段代码体现了几个原则：

  • 只捕能预期的异常：TimeoutError、OSError、以及自己定义的 FetchError。程序里真出了 bug（比如 TypeError）应该直接崩，让你看见。
  • 用自定义异常统一语义：外部调用者只需要 except FetchError，不用知道底层是超时还是 404。
  • from exc 保留因果：日志里能看到「超时」是怎么导致「抓取失败」的。
  • 失败要计数、要留痕、要能交差：这是新闻工作的职业要求，也是异常处理真正的价值。

场景二：给编辑部写一个「报纸版面文本清洗」脚本，坏行跳过但要报告

排版系统导出的文本常常不干净：有的行日期格式不对，有的行字数异常， 有的行干脆是空行。你要清洗出干净数据，同时又得知道「丢了多少、为什么丢」—— 否则领导问「怎么少了 12 条」你答不上来。 

import re
import logging
from dataclasses import dataclass, field

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

class RowFormatError(Exception):
    """单行数据不符合约定格式。"""
    def __init__(self, line_no, reason, raw):
        self.line_no = line_no
        self.reason = reason
        self.raw = raw
        super().__init__(f"第 {line_no} 行：{reason}")


date_pattern = re.compile(r"^(\d{4})-(\d{2})-(\d{2})$")

@dataclass
class CleanStats:
    ok: int = 0
    failures: list = field(default_factory=list)     # [(line_no, reason)]

    def add_failure(self, line_no, reason):
        self.failures.append((line_no, reason))


def parse_row(line_no, raw):
    """把一行 'YYYY-MM-DD 正文' 解析成 (日期, 正文)。坏行主动抛异常。"""
    raw = raw.rstrip("\n")
    if not raw.strip():
        raise RowFormatError(line_no, "空行", raw)

    parts = raw.split(" ", 1)
    if len(parts) != 2:
        raise RowFormatError(line_no, "缺少正文字段", raw)

    date_str, body = parts
    if not date_pattern.match(date_str):
        raise RowFormatError(line_no, f"日期格式不对：{date_str!r}", raw)

    if len(body) < 5:
        raise RowFormatError(line_no, f"正文过短（{len(body)} 字）", raw)

    return date_str, body


def clean_file(path):
    stats = CleanStats()
    cleaned = []

    with open(path, encoding="utf-8") as f:
        for line_no, raw in enumerate(f, start=1):
            try:
                cleaned.append(parse_row(line_no, raw))
            except RowFormatError as exc:
                stats.add_failure(exc.line_no, exc.reason)
                logging.info("跳过 %s", exc)      # 预期内的坏数据：记录后跳过
            else:
                stats.ok += 1
            # 没有 finally：这里不需要释放资源，with 已经负责了

    return cleaned, stats


cleaned, stats = clean_file("版面文本.txt")
print(f"清洗完成：成功 {stats.ok} 行，跳过 {len(stats.failures)} 行")
if stats.failures:
    print("跳过原因汇总：")
    reason_counts = {}
    for _, reason in stats.failures:
        reason_counts[reason] = reason_counts.get(reason, 0) + 1
    for reason, n in sorted(reason_counts.items(), key=lambda kv: -kv[1]):
        print(f"  {reason}: {n} 行")

这个脚本的设计要点：

  • 坏行用 raise 表达，不返回 None：因为「解析失败」和「解析出空值」是两件不同的事，用异常区分得更清楚，也不会在下游悄悄传播 None。
  • 捕获的是自定义异常，不是 ValueError 或 Exception：这样如果代码里真出了别的 bug（比如变量名写错），它会正常崩出来被你发现。
  • 跳过也留痕：logging.info + 统计对象，最后能给出「跳过原因汇总」，这才是可交付的清洗脚本。
  • 该用 with 的地方别用 finally：文件资源交给 with 管，finally 在这里没有存在必要。

6. 概念辨析

辨析 1：语法错误 vs 异常

# 语法错误：程序根本不会开始执行，整个文件都跑不了
while True print("hi")
# SyntaxError: invalid syntax

# 异常：程序跑起来了，跑到某一步才崩
def f():
    return 1 / 0
f()
# ZeroDivisionError: division by zero

关键区别：语法错误不能用 try 捕获（除了用 compile() / exec() 动态执行代码的场景）。 因为它发生在「编译」阶段，比 try 还早。所以你不可能用 try 兜住一个少写了冒号的程序—— 唯一办法是改正它。

辨析 2：except: pass vs except Exception as e: 记录 + 处理

# ❌ 吞掉一切，包括 Ctrl+C
try:
    危险操作()
except:
    pass

# ✅ 精确捕获 + 记录 + 明确后续动作
import logging
try:
    危险操作()
except (TimeoutError, ConnectionError) as e:
    logging.warning("网络问题，本次跳过：%s", e)
    # 明确的下一个动作：跳过、重试、或用默认值

except: pass 有三个问题：① 它捕获 KeyboardInterrupt，让程序无法用 Ctrl+C 停止； ② 它让所有错误信息永久消失，事后无从排查； ③ 它把「预期内的失败」和「代码 bug」混为一谈。 真正想「出错就跳过」时，应该明确写出跳过哪类错误，并留下记录。

辨析 3：try 里塞得越多越好？

# ❌ try 太长：任何位置的 ValueError 都会被误判成「读文件失败」
try:
    rows = 读CSV("a.csv")
    avg = sum(int(r["值"]) for r in rows) / len(rows)
    title = rows[0]["标题"].strip()
except ValueError:
    print("读取数据失败")     # 这三个位置都可能抛 ValueError，含义完全不同

# ✅ try 只包住「一个可能失败的动作」
try:
    rows = 读CSV("a.csv")
except (OSError, ValueError) as e:
    print(f"读取数据失败：{e}")
    raise

avg = sum(int(r["值"]) for r in rows) / len(rows)   # 这里的错应该暴露出来
title = rows[0]["标题"].strip()

判据：问自己「except 里的那句话，能不能准确描述 try 里任何一行的失败原因？」 如果不能，说明 try 太大了。官方的 else 子句就是为了解决这个而存在的。

辨析 4：finally vs with

# finally 版本：能用，但啰嗦
f = open("news.txt", encoding="utf-8")
try:
    data = f.read()
finally:
    f.close()

# with 版本：官方推荐，一行搞定，异常安全
with open("news.txt", encoding="utf-8") as f:
    data = f.read()

with 本质上是 try/finally 的语法糖（官方称之为「预定义的清理操作」）。 凡是支持 with 的对象（文件、锁、数据库连接、csv 的 reader 等）， 都优先用 with。只有对象不支持 with、或需要跨函数生命周期管理时，才手动用 finally。

辨析 5：raise ... from exc vs raise 新异常

# ❌ 丢掉原因
try:
    open("数据库.sqlite")
except OSError:
    raise RuntimeError("无法打开数据库")

# ✅ 保留因果链
try:
    open("数据库.sqlite")
except OSError as exc:
    raise RuntimeError("无法打开数据库") from exc

# ✅ 明确切断因果（不想暴露底层细节时）
try:
    open("数据库.sqlite")
except OSError:
    raise RuntimeError("服务暂时不可用") from None

三者的 Traceback 长度和清晰度差别很大。 第一种你会看到「During handling of the above exception, another exception occurred」这种隐式链（因为异常发生在 except 块里，Python 会自动链接）， 但语义上不够明确；第二种用 from 明确表达「直接原因」； 第三种则完全隐藏底层细节——适合面向外部用户的接口。

辨析 6：`assert` vs `if ... raise`

# assert：只用于「开发期自检」，可以被 python -O 关掉
def ratio(part, total):
    assert total > 0, "总数必须为正"
    return part / total

# if + raise：用于「运行期必须成立的校验」
def ratio(part, total):
    if total <= 0:
        raise ValueError(f"总数必须为正，实际是 {total}")
    return part / total

区别在于：assert 用 python -O 运行时会被整个删掉， 所以绝对不能用它做「数据校验」——那等于在生产环境里没有校验。 assert 只适合写「这一步按我的推理不可能是这样」的断言，或者写测试。

7. 自测问题

Q1：看到下面这段报错，你应该从哪一行开始读？第一步该做什么？ 
Traceback (most recent call last):
  File "main.py", line 30, in <module>
    run()
  File "main.py", line 22, in run
    report = build_report(rows)
  File "main.py", line 15, in build_report
    total = sum(int(r["阅读量"]) for r in rows)
ValueError: invalid literal for int() with base 10: '1.2万'
从最后一行开始读，再往上找第一个「我自己写的文件」的行。 这里结论是 ValueError: invalid literal for int() with base 10: '1.2万'； 现场在 main.py 第 15 行，试图把 '1.2万' 转成整数。 第一步应该是想清楚：这个字段里出现了「1.2万」这种非纯数字格式， 需要在转换前先做清洗（比如把「万」乘 10000），而不是去改 build_report 的调用。
Q2：try 子句里有 5 行代码，第 3 行抛了异常且被 except 接住。第 4、5 行会执行吗？
不会。官方说明：「如果在执行 try 子句时发生了异常，则跳过该子句中剩下的部分」。 会直接跳到 except 子句，然后继续执行 try/except 代码块之后的语句。 这也是为什么不要在一个 try 里塞太多行——出错时后面的都不执行，你得自己去想「哪些已经做了、哪些没做」。
Q3：下面两个 except 的顺序会有什么影响？为什么？ 
# A
except OSError:
    ...
except FileNotFoundError:
    ...

# B
except FileNotFoundError:
    ...
except OSError:
    ...
A 里的 except FileNotFoundError 是死代码，永远不会执行。 因为 FileNotFoundError 是 OSError 的子类，官方说「匹配的异常将是该类本身的实例或其所派生的类的实例」， 所以 except OSError 会先接住它。 B 是正确的顺序：具体的写前面，笼统的写后面。
Q4：finally 子句在什么情况下不会执行？
官方定义是「不论 try 语句是否触发异常，都会执行」，实际中几乎没有「不会执行」的情况。 唯一需要提防的是「finally 里有 return/break/continue」—— 它不是不执行，而是它会吃掉正在传播的异常，导致你以为是别的问题。 官方明确说这种写法「可能会引起混淆，因此不鼓励使用」，3.14 起会发 SyntaxWarning。 所以真正的结论是：不要在 finally 里写 return。
Q5：同事说「我在代码外面包了一层 try: ... except: pass，现在不报错了」。你怎么看？
报错消失不等于问题解决。三个具体后果：① 它连 KeyboardInterrupt 都捕获，Ctrl+C 停不掉程序； ② 所有错误信息永久丢失，出问题时无从排查；③ 后续代码拿到 None 或空结果，会在离原因很远的地方崩，更难查。 应该改成：精确列出预期异常、用 logging 记录、明确「接下来怎么办」（跳过/重试/用默认值/向上抛）。
Q6：下面这个函数的返回值是什么？为什么？ 
def f():
    try:
        return "正常"
    finally:
        return "finally"
返回 "finally"。官方原话：「如果一个 finally 子句包含一个 return 语句， 返回的值将是来自 finally 子句的 return 语句，而不是来自 try 子句的 return 语句。」 官方还补了一句「这可能会引起混淆，因此不提倡使用」。 实践规则：finally 只做清理和记录，不要写 return。
Q7：except Exception 为什么接不住 KeyboardInterrupt？这是设计缺陷吗？
不是缺陷，是刻意设计。官方在 KeyboardInterrupt 条目里写明： 「该异常继承自 BaseException，以免被捕获 Exception 的代码意外捕获而导致解释器无法退出」。 SystemExit（由 sys.exit() 引发）和 GeneratorExit 同样是直接继承 BaseException。 这三个都不是「错误」，而是「控制流信号」，所以它们不该被普通的错误处理逻辑拦下来。
